# 服务启动与停机

本流程适用于单进程 SQLite API。以下命令只描述机制；第 8 步验证只在本机合成数据库上执行，未修改生产进程管理器或生产数据。

## 启动

入口为 `node aural-api/server.js`（通常在 `aural-api` 内执行 `npm start`）。先绑定 `HOST`/`PORT`，再初始化及验证审计链、初始化内容目录，最后开放请求和后台计时器。初始化期间端口可能已绑定，但请求返回 503 `SERVICE_STARTING`，不能把端口可连接当作就绪。初始化或监听失败会排空已开始工作、断开数据库，以非零码退出；端口占用不会先启动自动备份或维护。支持 `PORT=0`，仅供本地随机端口测试。

## 正常停止

向 API 的实际 Node PID 发送 `SIGTERM` 或 `SIGINT`。停止状态立即生效：关闭监听入口及空闲连接，已有连接的新请求返回 503 `SERVICE_STOPPING`；停止自动备份、维护、通知领取与限流清理计时器。已接受的 HTTP 处理器、事务队列、响应后的 API 日志、告警和提交后任务继续完成。客户端断连只释放连接，不代表业务处理已经结束。

正在生成的备份、正在执行的隔离恢复演练会等待其完整 Promise，包括验证、结果写回、临时目录/锁文件清理、独立数据库客户端断开。通知停止领取新工作；正在发送的请求完成并持久化结果，未发送 outbox 留待下次启动。最后确认任务及 SQLite 队列为空，断开主数据库，输出 `Service stopped` 并以 0 退出。重复停止信号复用同一次排空。

`SHUTDOWN_TIMEOUT_MS` 默认 60000，允许 1–300000 的整数毫秒。超过期限输出 `Service shutdown_failed`、`SHUTDOWN_TIMEOUT` 和固定类别任务计数，关闭连接并以 1 退出。**这是未完成排空的故障退出**：不能承诺事务后的业务补偿、备份锁或演练临时目录全部完成清理。重启后须检查失败/运行中记录和备份完整性。`SIGKILL`、断电、运行时崩溃和事件循环被同步任务阻塞，也不在正常排空保证范围。

## 进程管理器约束

使用 PM2 的现有安全部署脚本会只读校验运行配置：PM2 必须显式记录运行 API 的 `SHUTDOWN_TIMEOUT_MS`；缺失时无法证明旧进程是否从 `.env` 读入了更长预算，门禁会拒绝继续。API `kill_timeout` 必须至少为旧进程和新配置中较大的 `SHUTDOWN_TIMEOUT_MS` 加 5000。默认预算对应至少 65000ms；缺失或不足时部署门禁拒绝继续。路径校验保留。生产配置是否满足此约束未现场验收，本地仅使用模拟 PM2 列表验证，不执行真实 PM2 操作。

如果使用 PM2 `wait_ready`，API 会在初始化完成后发送 IPC `ready`；须另行给初始化配置合理的 `listen_timeout`。容器或其他管理器同样须提供比应用预算更长的终止宽限期。调整预算应依据实际数据规模和本地/预发布演练，不能用延长事务等待或增加 Prisma 线程数掩盖锁争用。

## 本地验证

`TOKIO_WORKER_THREADS=2 npm test` 包含动态任务排空、事务提交后任务、启动/初始化中停止、真实主入口监听冲突与信号终止测试。故障注入只在测试 preload 中，业务 API 不包含测试接口。新增子进程测试使用 `logs/step8-20261013/` 下独立迁移的虚构库与素材，通知渠道关闭；每例释放自己创建的进程和目录。浏览器证据及完整执行结果见 `SECURITY_HARDENING.md` 第 8 步。
