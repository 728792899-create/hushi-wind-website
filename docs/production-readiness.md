# 生产准入清单与待决策事项

本清单以第 14 步现场复核为准。**本地加固、指定提交的 CI 通过，与生产准入是独立结论；当前未授权生产操作，未部署，未完成生产验收。** 每次发布都须重新填证据，不能用后台“生产就绪”评分、旧 CI 或这份清单的存在代替验收。

用户随后已确认：技术方案由 Codex 准备，沿用现有单机架构，不接新服务、不增加费用；服务器、域名和正式资料由用户后补，资料未齐的栏目首发不公开；本期只做上线准备，正式部署前再次由用户确认。具体执行方案、一次性资料表与最终确认单见[单机上线准备方案](single-host-launch-plan.md)。不继续扩展加固范围，也不重复询问已确认的架构和权限规则。

## 使用方式

每项登记：执行人、复核人、时间、环境、完整源码 SHA、证据位置、结果与未决问题。责任人由用户指定；表中的角色是待分配职责，不代表已有人员或审批制度。含账号、路径、配置、数据库或客户资料的证据保留在受限位置，公开仓库仅记录脱敏结论。

本地工作限定 `~/Projects/hushi-wind-website`、`codex/admin-core-redesign`。禁止使用 iCloud 原目录、强推、清工作树或重写已推送历史。原演示库未迁移，不得连接新版 API。以下“待验收”不会在本步自动执行。

## 本地检查及副作用边界

在仓库根、只有合成夹具的环境运行：

```bash
TOKIO_WORKER_THREADS=2 npm test
DATABASE_URL=file:./dev.db VITE_API_BASE=https://api.example.invalid VITE_SITE_URL=https://www.example.invalid NUXT_PUBLIC_API_BASE=https://api.example.invalid NUXT_PUBLIC_SITE_URL=https://www.example.invalid npm run quality
npm --prefix aural-admin run check:admin-ui
npm run check:admin-colors
npm run check:bom
git diff --check
```

这里 `quality` 的 `DATABASE_URL` 只用于 Prisma schema validate，不启动业务 API、不迁移该库。测试创建隔离夹具；构建写本地输出；依赖审计会访问现有 npm 公告服务。新增未跟踪文件须先确认纳入提交再跑 BOM（它枚举 Git 跟踪文件）。远端 CI 必须重新核对候选完整 SHA、结论和检查注释。

| 工具/入口 | 实际副作用与可证明范围 |
|---|---|
| `preflight` | 加载 `.env` 并只读验证配置/目录，不能代替真实网络和账号验收；不要公开完整环境输出 |
| `postdeploy:check` | 加载 `.env` 并访问指定站点/API；默认不管理员登录，显式开启登录会写登录记录。健康/页面/鉴权边界检查不能证明真实恢复目标 |
| `full-acceptance-check.js` | 即使关闭 CRUD 测试也会 POST 管理员登录；其中“最近备份”只查非空 `.db` 和时间，不能证明清单、素材或可恢复 |
| `check:disk` / `alert:test` | 前者异常时可写告警并发 webhook；后者会写库，配置渠道后可真实发送。不是纯只读操作，本步不运行 |
| `check:audit` | 指向明确获准的副本，只读验证已有链，不初始化历史基线 |
| `drill:restore` | 不加载 `.env`；显式本地完整包和 scratch 目录，复制到独立库验证并虚构续写，清理本次副本；不覆盖源库。见恢复文档 |
| `drill:capacity` | 只造合成数据、启动自己的回环进程、测试在途停止；消耗本地 CPU/磁盘。见容量文档，不能替代生产压测 |
| `safe-deploy` / `deploy:production` | 会安装、构建、停进程、备份、迁移、切链接、重启；失败可能回滚数据，**不是演练入口**。本步仅模拟外部动作，不执行真实脚本发布 |

## 获准后的发布与接管原则

符合现有布局的升级入口为 `aural-api/scripts/safe-deploy.js`（`deploy-production.js` 委托它），要求已有 current 旧 release 和 API/Web PM2 进程；**首次空机初始化不能使用它**。先复核 stage/releases/current/shared 布局、实际 PM2 配置、依赖锁及候选质量门禁；通过后才建立维护门禁、停止旧 API、创建完整恢复点并迁移。切换和重启后的健康/页面/鉴权检查通过才能解除门禁。回滚也要完成就绪核验；回滚失败保留门禁并交由获准人员检查，不把“执行了 restart”记录为“已恢复”。

当前脚本自动回滚只还原数据库和 current，不还原 uploads 或旧进程环境；普通发布必须满足素材/持久配置不变的条件，其他变更单列恢复方案。首次初始化、配置注入、内容公开及完整灾备边界详见[单机方案](single-host-launch-plan.md)。

生产执行参数、备份路径、恢复目标与人工接管人按用户提供的事实填入最终确认单，**在正式部署确认之前供审阅，确认之后才执行**。本清单不提供绕过保护的覆盖解压、直接拉取重启或破坏历史操作。正常退出无法保证强杀/断电下任务收尾；故障后须核对数据库、备份/素材和未完成记录。
