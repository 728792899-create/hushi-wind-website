## 3. 单机布局与配置草案

建议使用既有反向代理承接 HTTPS：官网转至 Nuxt Node，API 与公开素材转至 API，后台只提供 `aural-admin/dist`。API 与 Nuxt 仅监听回环，分别拟用 `127.0.0.1:1337`、`127.0.0.1:3100`；端口须在目标机盘点后确定。生产不用 Vite 开发服务器，不向公网暴露数据库、备份、日志、源码或配置目录。

以下 `/srv/hushi` 只是拟定布局，不是已存在的生产路径：

```text
/srv/hushi/
  stage/<候选 SHA>/           # 干净的候选源码，不与 releases 互相包含
  releases/<发布 ID>/         # 三端源码、锁文件和当次构建输出
  current -> releases/<ID>    # 原子切换的符号链接
  shared/
    prod.db                  # SQLite（运行时可能有 WAL/SHM）
    uploads/                 # 仅可公开的正式素材
    backups/                 # db + manifest + assets 完整包
    logs/                    # 受限运行记录
    config/                  # 受限配置，不属于静态站点根目录
    deploy-write-gate         # 仅维护期间存在
```

持久目录均为绝对路径，位于 releases 之外；目录所有者和最小文件权限按实际运行账号核定。SQLite 保持 API 单实例，不启用 PM2 cluster 或多副本。Nuxt 使用 `.output/server/index.mjs`，后台静态根指向 `current/aural-admin/dist`。

| 配置组 | 准备规则 |
|---|---|
| API 路径 | `DATABASE_URL=file:/实际路径/shared/prod.db`、`UPLOAD_DIR`、`DATABASE_BACKUP_DIR`、`DEPLOY_WRITE_GATE_FILE` 指向上述持久目录 |
| API 网络 | 显式 `HOST=127.0.0.1`，确认 `PORT`；生产默认监听地址并非回环，不能省略 HOST 后假定已隔离 |
| Nuxt 网络 | 按实际 Nitro 入口设置独立 `NITRO_HOST=127.0.0.1`、`NITRO_PORT`；不向两个进程盲目注入同一个 PORT |
| 公共 URL | 官网目标为 `https://dayouyusd.com`；后台/API 的具体路径或子域方案待实际 DNS/TLS/代理条件核实。将实际方案一致注入 `PUBLIC_SITE_URL`、`PUBLIC_ADMIN_URL`、`API_PUBLIC_URL`、`UPLOAD_PUBLIC_BASE`；CORS 只列精确 origin；`TRUST_PROXY` 仅信任实际代理来源 |
| 构建 URL | 后台 `VITE_API_BASE` / `VITE_SITE_URL`、官网 `NUXT_PUBLIC_API_BASE` / `NUXT_PUBLIC_SITE_URL` 与公共 URL 一致；SSR 的 `NUXT_API_INTERNAL_BASE` 可指向本机 API。域名变化后重建重审，不复用示例配置的产物 |
| 账号与密钥 | 非默认管理员、强密码、随机会话密钥；在受限环境配置。管理员登录及 MFA 单列验收，不把匿名健康检查当作账号验收 |
| 通知与策略 | 不接新通知服务；`ALERT_WEBHOOK_URL` / `ALERT_EMAIL_TO` 保持空，告警留在后台；沿用已批准权限与留存，默认周期核验 24 小时 |
| 停机与就绪 | `SHUTDOWN_TIMEOUT_MS` 保持现有 60000ms 起点，实际 PM2 env 必须显式记录；`kill_timeout ≥ max(旧,新预算)+5000ms`。发布检查默认总等待 60000ms、单请求含正文 10000ms、重试间隔 1000ms；均不代表业务 SLA |

**配置文件不会自动生效。** [load-env.js](../aural-api/scripts/load-env.js)默认只读脚本所属 `aural-api/.env`，不覆盖已有进程环境；[safe-deploy.js](../aural-api/scripts/safe-deploy.js)复制 release 时排除 `.env*`。只把文件放进 `shared/config/` 不足以让 API、PM2、构建及发布检查读取它。目标确定后，准备与既有管理器一致的显式配置注入方式，核对每个进程的路径、端口和公开 URL；检查输出只保留脱敏值。配置变更不夹带在普通版本回退中。

根目录 `build:admin` / `build:website` 脚本仍带历史固定域名，不能直接当作正式构建命令。实际候选在明确环境变量后调用各子项目构建或经已验收的发布入口执行；依赖使用锁文件和 `npm ci`。Node 选择满足当前锁文件的 22 系列补丁版本，目标机再核对，不按旧指南安装 Node 18/20。

“保存修改草稿”是并行编辑功能，**不会下架原来已发布的记录**；下架须确认记录的实际公开状态。[content-workflows.js](../aural-api/lib/content-workflows.js)与[公开 API](../aural-api/server.js)为依据。`/uploads` 是静态公开路径，隐藏下载记录不会撤销已知文件 URL；首发素材目录只接收确认可公开的文件，不导入未批准的私人文件。既有数据不删除，若旧站已有敏感文件公开，另列具体处置供用户确认。

旧照片以实际作品页与许可核验记录为准，通用商业使用许可不等于人物代言、产品型号或自有场地证明。只复制首发批准清单中的图片，不整目录导入旧 uploads；来源尚未核实的图片不计作已批准素材。原演示商品、人物姓名、公司历史和售后承诺不随设计复用恢复。

## 5. 分阶段执行与停止条件

### A. 现在可完成的准备

在本仓库的隔离环境完成已批准首发内容、原设计复用、目标配置草案、依赖/产物及必要隐藏处理的验证。获准的旧库副本只在受限本地环境做迁移与完整恢复演练。每项结果绑定当次候选，不能把同机旧演示服务的页面当作新候选运行证据。

本地验收只覆盖候选变化：自动测试和质量门禁；390 手机 / 1440 桌面的首发页面、菜单、键盘、实际下载与获准表单；匿名直达未公开栏目、搜索、sitemap 和 API 的反向验证；后台权限与备份/审计关键流程。真实内容截图、试验数据与配置不提交公开仓库。

远端连接恢复后，先核实目标身份、既有进程、目录和数据，再在已授权范围内执行必要部署并记录副作用。当前尚未远端写入或修改 DNS；不能把 `ssh-keyscan` 成功、候选本地通过或用户授权写成部署完成。真实通知仍不在本期范围内。

### B. 已授权范围的执行前登记

填写本方案第 7 节，按目标机实际状态确定首发/升级路线、操作范围和恢复点。必需证据缺失或演练失败时说明具体缺项，不新增一轮泛化加固，也不重复询问已有指定部署授权。连接与候选验证完成后按适用的 C 或 D 执行；涉及授权范围实质变化时另询。

### C. 目标机首次初始化（满足执行条件后）

现有安全发布脚本要求已有 `current` 指向旧 release，且 API/Web 已受 PM2 管理，因此**不能用于空机首次初始化**，也不能制造一个空旧 release 绕过校验。

1. 先按获准方案准备目录、运行账号、配置、候选构建及代理规则，外部入口保持未开放。生产写入从这一步开始，必须已有明确授权。
2. 指向独立的新正式数据库，按锁文件安装、生成 Prisma 客户端、执行迁移，再以回环监听启动。禁止导入 `dev.db` 或演示种子。
3. 在仅维护人员可达的入口进行受控初始化：当前 API 启动只初始化审计和目录分类；管理员记录在首次 `/api/auth/login` 建立，`SystemConfig` 在首次 `/api/config` GET 时按需建立。健康检查要求这两表各至少一条，**不能在空库上等待健康自动转绿，也不能把这个 GET 当成绝对无写入**。初始化后设置正式全局配置，登录并验收 MFA，导入/发布仅获准内容。
4. API 的部署门禁主要阻止写请求，但放行登录/刷新及 GET；它不阻断外部读取，也不等于入口隔离。首发隔离由代理/访问范围保证，初始化所需写入在受限入口完成，不能依靠一个门禁文件当作全站关闭。
5. 校验数据库与审计、创建完整备份并在独立 scratch 演练；核验私有路径不可公开、实际配置、管理员、首发栏目与下载。登记真实耗时/磁盘证据，失败保持入口关闭。
6. 把已验收 release 作为后续可回退基线：`current` 链接及 PM2 的 `pm_exec_path` / `pm_cwd` 都按 current 路径注册，并显式登记停机预算。不能仅验证链接指向就推断管理器会跟随切换。
7. 在已授权范围内开放入口并复验，切换前保存原 DNS 记录及明确回退步骤。新主机首个 release 没有本机旧版本可回退；失败时撤回新入口、停止本次新进程并保留数据/日志，按已记录的 DNS 回退方案处理，不声称仅恢复解析就已恢复旧站业务。

### D. 替换目标机既有站点或后续升级（满足执行条件后）

若目标机既有站点不符合 current/shared/PM2 布局，先单列既有基线的接管与完整备份方案；不能直接把 `safe-deploy` 用于未知布局。保留旧站数据、配置及启动信息，不覆盖原目录。若发现要接管无关业务、迁入未授权旧数据或扩大操作范围，只就该变化另询；已批准的域名 A 记录替换不等于授权操作旧地址上的主机。

满足脚本布局后的顺序为：检查当次环境与就绪预算 → 检查旧 current、PM2 及排空预算 → 在独立新 release 安装/测试/审计/构建 → 建维护门禁 → 停旧 API → 完整备份 → 迁移并检查数据库 → 切 current → 重启 API/Web → 检查健康、鉴权边界、页面和当次后台 dist → 成功后解除门禁。脚本会真实停机、迁移及可能恢复数据库，绝不是只读或演练入口。

当前脚本回退会还原数据库和 current，再重启并验证旧版本；**不还原 uploads，也不恢复旧进程的完整环境配置**。因此本路线仅用于兼容现有持久配置、不会改写/删除素材的版本发布；素材、密钥、域名、运行配置变更先拆出明确操作及回退步骤，不能宣称脚本包办。完整灾难恢复另按完整备份包、匹配代码与受限配置执行，不能以数据库回滚替代。

回滚健康失败时保留维护门禁并人工接管。网站已恢复业务写入后再发现问题，不自动覆盖回发布前数据库；先限制新写入、保留当前恢复点并说明会丢失哪些新数据，由用户决定恢复点和处置。正常排空不能保证强杀或断电下任务完成。

## 6. 本期验收标准与风险边界

| 检查 | 成功证据 | 不代表什么 |
|---|---|---|
| 源码与构建 | 候选完整 SHA、锁文件、全部质量检查、相同 SHA 的 CI；当次产物来源与运行时审计 | 旧 CI 或旧包不能给新域名/内容背书 |
| 访问与首发内容 | HTTPS/代理/来源一致；390/1440 实际首发页面可用；未公开栏目与数据不能从固定入口、直达、搜索或 sitemap 露出 | 不把菜单隐藏当栏目关闭，不把示例图验收当正式图验收 |
| 账号与数据 | 人工登录/MFA、既定角色边界、数据数量/字段/审计一致；无演示凭据或测试数据 | 匿名健康接口成功不等于业务验收 |
